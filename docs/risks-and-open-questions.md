# SathyaScan — Missing Requirements & Technical Risks

The PRD is thorough on product behavior but silent or ambiguous on the items below. Each entry states the gap, a recommended default, and its **current status** now that the user has locked in decisions on August 13, 2026 (see [`decisions.md`](decisions.md), the authoritative record of what's settled).

**How to read this document now**: most items below are no longer open — they carry a `**Status: LOCKED**` line pointing at the relevant `decisions.md` section. A few remain genuinely open because they were deliberately left unresolved (mandatory legal/professional review, or a number only real usage data can inform) rather than decided by engineering. This file keeps its original risk analysis text as context for *why* each decision was made; `decisions.md` is authoritative for *what was decided*.

## LLM & evidence-search budget
Each analysis may trigger several evidence searches plus multiple Claude calls (claim extraction, stance judgment, fusion, translation). The PRD gives no budget.
**Status: LOCKED (mechanism)** — see [decisions.md §1](decisions.md#1-llm--evidence-search-budget). Two-tier limiting (per-analysis caps + global circuit breaker), fully config-driven, `insufficient_evidence` as the safe fallback on limit hit — a distinct, precisely-defined outcome from `unverified`, never a signal toward true/false (see [decisions.md §1A](decisions.md#1a-result-status-definitions--unverified-vs-insufficient_evidence), locked in a follow-up round on 2026-08-13). **Still open**: the actual numeric values to put in config — set before Phase 2 real-user traffic, tune with real cost data.

## AI-detection accuracy has no SLA
AI-generated image/video/audio detection is a genuinely hard, actively adversarial problem — generators evolve faster than detectors, and models drift. The PRD gives no accuracy target.
**Status: LOCKED (approach) — interface implemented in Phase 3, NO real provider wired.** See [decisions.md §2](decisions.md#2-ai-generated-media-detection). The `ImageAnalysisTool` contract, hedged-language rendering, and mandatory provider/version display fields all exist (`app/agent/tools/image_analysis.py`), but `NullImageForensicsProvider` is the only wired implementation — a confirmed Phase 3 scope decision to avoid an unnecessary new paid external API without real credentials, not a silent gap. Every image-derived claim's visual-authenticity check is currently `unavailable`, disclosed to the user, and never gates classification. **Still open**: acceptable false-positive/negative tolerance is unchanged and still a product/legal judgment call; a real provider integration and its benchmark are future work.

## Copyright / ToS risk of reverse-tracing and evidence scraping
PRD §7 asks for "reverse/source tracing (where feasible and compliant)" and evidence retrieval implies pulling from news sites.
**Status: LOCKED** — see [decisions.md §3](decisions.md#3-evidence-sources--tiered-system). Licensed search APIs, snippet-only storage (no full-text scraping), `robots.txt` respected for direct URL fetches. No open question remaining here.

## WhatsApp messaging costs
Meta charges per conversation; the PRD names no budget. Compounding this, "Check This Tomorrow" follow-ups almost always require **paid template messages** since they fall outside the 24-hour free-form window (full detail in `whatsapp-integration.md`).
**Status: LOCKED (scope decision resolves the MVP risk)** — see [decisions.md §4](decisions.md#4-whatsapp--mvp-messaging-scope). MVP ships with within-window replies only; no proactive/template messaging at all, which removes this cost/approval dependency from the MVP critical path entirely. **Still open, but no longer MVP-blocking**: a cost model and Meta use-case confirmation are still needed before Scheduled Checks (decisions.md §14) is ever built, whenever that becomes relevant.

## Defamation / legal exposure
Labeling a claim "False" carries real legal risk, especially for political, election, and government-scheme content — exactly the categories PRD §18 names as high-traffic topics.
**Status: LOCKED (policy) — PENDING MANDATORY LEGAL REVIEW** — see [decisions.md §5](decisions.md#5-false--misleading-classification). Evidence-first wording, a raised evidence bar for high-impact categories that defaults to `unverified` when a completed investigation doesn't clear it (or `insufficient_evidence` if the investigation was cut short before it could — see [decisions.md §1A](decisions.md#1a-result-status-definitions--unverified-vs-insufficient_evidence)), universal appeals access, and an explicit rule that the system is never optimized to maximize "False" counts. **Still open**: legal counsel review of the specific evidence-bar thresholds before public launch — this is a hard launch gate, not a nice-to-have.

## Abuse / illegal content handling — unaddressed by the PRD, not optional
SathyaScan is a public inbound WhatsApp surface accepting arbitrary user-submitted media. The PRD never discusses what happens if a user forwards illegal content (e.g. CSAM, terrorism-related material) "for verification."
**Status: LOCKED (interface IMPLEMENTED in Phase 3) — PENDING MANDATORY LEGAL REVIEW, PUBLIC LAUNCH HARD-BLOCKED** — see [decisions.md §6](decisions.md#6-illegal--abusive-content-incl-csam). The safety-gate stage is now real, not just designed: it runs before any media-analysis tool touches a file (`app/agent/safety_gate.py`), is non-bypassable in code, fails closed on any provider error, and records minimal, content-free events (`safety_gate_events` — implemented and migrated in Phase 3). `NullSafetyProvider` is the only wired provider — it passes all content through and logs a loud warning on every use. **Deliberately still open**: the detection vendor and reporting procedure are not specified anywhere in this documentation set or codebase — inventing one without qualified legal/professional input was explicitly avoided per the user's instruction, reconfirmed at the start of Phase 3. **The system must not be exposed publicly until this review is complete**, full stop — check `GET /health`'s `safety_gate_provider_configured` field as a live, operational signal of this.

## Phone number handling
The PRD's `identifier_hash` (§35) alone is insufficient: the system must also retain the actual phone number (encrypted) to send WhatsApp replies at all — a hash alone can't route a message.
**Status: LOCKED** — see [decisions.md §7](decisions.md#7-phone-number-security). `phone_number_encrypted` (KMS) + `phone_number_hash` (keyed HMAC with a server-side pepper), now with explicit, hardened rules: never logged, never returned by any dashboard API, keys/secrets live outside the DB and source. No open question remaining here.

## Multilingual evidence quality
Evidence sources (government portals, reputable news, fact-checking orgs) skew heavily English. A Malayalam or Tamil claim needs to be checked against evidence that may not exist in that language.
**Status: LOCKED (approach)** — see [decisions.md §3](decisions.md#3-evidence-sources--tiered-system). Translate-search-translate-back approach with a faithfulness caveat, tiered `source_credibility_registry` seeded with Indian fact-checkers. **Still open**: the actual curated, expert-reviewed regional-language source list is content-curation work, not a decision resolvable in this document — needs to happen before Phase 2 launches to real users.

## Scheduling infrastructure
Not specified by the PRD.
**Status: LOCKED** — Celery + Redis + Celery Beat, unchanged by this decision round. No open question remaining here; note that its only MVP use is the Privacy Mode purge jobs (decisions.md §8), since "Check This Tomorrow" itself no longer has a fixed place on the MVP/V2 timeline (decisions.md §4/§14).

## GPU / compute cost
Not addressed by the PRD at all — likely the single largest infra cost line item once video/audio analysis (V2/V3) goes live, and the user's stated preference is a lean/bootstrapped MVP.
**Status: Deliberately still open, deferred by design** — third-party APIs absorb this for MVP/V2 (unchanged). **Still open**: no compute budget has been set, and none needs to be until V3 planning begins — this was not part of the current decision round because it isn't yet actionable.

## Data residency / India's DPDP Act 2023
Indian users' phone numbers and message content likely fall under India's Digital Personal Data Protection Act.
**Status: LOCKED (posture) — PENDING MANDATORY LEGAL REVIEW** — see [decisions.md §9](decisions.md#9-dpdp--privacy--design-posture) and [decisions.md §10](decisions.md#10-hosting) (hosting kept portable to India-region if required). Every DPDP-relevant mechanism (minimization, deletion, encryption, access control, auditability) is now a confirmed design requirement. **Explicitly not claimed**: SathyaScan is not described as DPDP-compliant anywhere in this documentation, and must not be until the legal review confirms it — this is now an explicit written rule, not just an implicit gap.

## OCR / ASR accuracy for Malayalam / Tamil
PaddleOCR and generic Whisper measurably underperform on these scripts and on Indian-accented speech relative to English/Hindi — a real pre-commit risk given Malayalam and Tamil are named PRD-required languages (§1).
**Status: LOCKED (process) — Phase 3 implements the OCR infrastructure (no engine wired); Phase "A-real" implements a GENUINE ASR provider (Sarvam AI) but keeps it opt-in; NEITHER benchmark has actually run.** See [decisions.md §11](decisions.md#11-malayalam--tamil--hindi--english). `OCRTool`'s provider interface (Phase 3, `NullOCRProvider` only) and `SpeechToTextProvider`'s interface (Phase 5, `app/agent/tools/speech_to_text.py`) are both built. For ASR specifically: `SarvamSpeechToTextProvider` (`app/integrations/speech_to_text_client.py`) is a real, correct client — selected after comparing it against Google Cloud Speech-to-Text (Sarvam is ~2-3x cheaper, purpose-built for 22 Indian languages incl. Malayalam/Tamil/Hindi/English with code-mixing support relevant to real WhatsApp voice notes, traded off against being a newer/less-proven vendor than Google) — but **no real Sarvam credentials exist in this environment**, so it has been tested only against a scripted `httpx.MockTransport` (`tests/unit/test_sarvam_stt_client.py`), never a live call, and stays OPT-IN behind `app/core/provider_selection.py` (`NullSpeechToTextProvider` remains the default). This does **not** satisfy decisions.md §11's benchmark-before-lock-in rule — activating real credentials makes the provider available to benchmark, it doesn't constitute the benchmark. For OCR specifically: a real provider (`ClaudeVisionOCRProvider`, `app/integrations/vision_ocr_client.py`) now exists and is opt-in behind `OCR_PROVIDER=claude_vision`, and the **measurement layer §11 requires is now built and runnable** — `app/agent/ocr_benchmark.py` (per-language CER/WER scoring) plus `scripts/run_ocr_benchmark.py` (CLI over a labelled manifest, writing to `benchmark_runs`). That closes the tooling half of this gate. It does **not** close the gate: no benchmark has been run, because no labelled Malayalam/Tamil/Hindi/English image corpus exists in this environment, and sourcing/labelling one is human work this build cannot do. Two measurement caveats are documented in the module and must be read before citing any figure it produces: infrastructure failures are reported separately and never averaged into accuracy, and CER is **code-point based, not grapheme based**, so it reads slightly pessimistic against Malayalam/Tamil specifically (stdlib has no grapheme segmentation; `regex`/`uniseg` would be a new dependency). Use it to compare engines against each other, not as an absolute accuracy claim. **Still open**: (1) sourcing real Sarvam credentials and running an actual benchmark against curated Malayalam/Tamil/Hindi/English voice-note samples before this provider is ever activated in production; (2) verifying Sarvam's English (`en-IN`) accuracy specifically, since their marketing centers Indian-language accuracy and their docs didn't make an explicit English-accuracy claim; (3) **sourcing a labelled OCR corpus and actually running `scripts/run_ocr_benchmark.py` against each candidate engine** — the runner exists, the data does not; (4) no equivalent ASR benchmark runner has been built (this round covered OCR only). Phase 5's architecture genuinely supports adding any of the four languages without redesign — `language_hint` is advisory, `detected_language` is what's actually used, and the transcript is never translated before claim extraction — confirmed by scripted Malayalam/Tamil/Hindi/English fixtures in both `tests/unit/test_speech_to_text_and_audio_forensics.py` (fake provider) and `tests/unit/test_sarvam_stt_client.py` (real provider's request/response mapping).

## Items added during this decision round (not in the original 13)

Two security requirements were added that weren't separately named in the original PRD or this document's first pass, both now locked in [decisions.md §15](decisions.md#15-security-release-gate): **SSRF protection** for the URL Analyzer/URL Safety Module (resolved-IP checking before any fetch, not just URL-string validation) and **prompt-injection defenses** (untrusted content — user text, OCR, transcripts, fetched URLs — is always passed to the LLM as data, never as instructions). SSRF protection is now **wired for real in both places it applies** — the Meta media downloader (Phase 3) and the URL fetcher (Phase 4, `app/web/fetcher.py`), which additionally re-checks every redirect hop, not just the first URL. Both requirements are still Phase 7 (formerly Phase 6, see phased-plan.md's reprioritization note) release-gate items in the sense that final verification (the full security checklist) happens there, but the URL-fetch-path implementation gap flagged at the start of Phase 4 is now closed. Phase 5's multimodal fusion layer (`app/agent/multimodal_fusion.py`) extends the prompt-injection discipline to a third untrusted-content source — video transcripts and OCR'd on-screen text — by structuring both as plain delimited data, never instructions, same as every other content source.

"Check This Tomorrow" is no longer analyzed here as an open risk — it's now a locked scope decision (cut from MVP entirely) with explicit, written preconditions for when V2 work on it can start. See [decisions.md §4](decisions.md#4-whatsapp--mvp-messaging-scope) and [§14](decisions.md#14-scheduled-check-this-tomorrow-explicitly-deferred-design-constraints-for-v2).

## Threat-intelligence API for URL Safety (Phase 4) — explicitly optional, not wired
phased-plan.md's Phase 4 scope names an "optional Safe Browsing–style API" for the URL Safety Module. Unlike OCR/image-forensics/safety-gate (which are blocked on legal review or a benchmark), this one is blocked purely on **credentials and a paid third-party subscription** (Google Safe Browsing, PhishTank, VirusTotal, or similar) that don't exist in this build environment.
**Status: LOCKED (scope) — interface implemented, `NullThreatIntelProvider` is the only wired provider.** See `app/agent/tools/url_safety.py`. Every OTHER URL Safety signal is real in this build — HTTPS/domain-pattern/redirect-chain/phishing-keyword/fake-login-form heuristics (all deterministic, no LLM, no credentials) and domain-age (real WHOIS lookups, `app/web/domain_age.py` — no credentials needed since WHOIS is an unauthenticated public protocol, confirmed with a live lookup during implementation). Absence of a threat-intel match is never treated as a verified "safe" signal — the same "absence of evidence isn't evidence of absence" caveat used throughout this document. **Still open**: sourcing real threat-intel credentials is a prerequisite for wiring a non-stub provider; not blocking for MVP since the feature was always marked optional.

## Audio/video AI-generation detection (Phase 5, updated Phase "B/C-real") — real client built, kept opt-in on cost grounds
decisions.md §2 requires third-party detection APIs, never self-hosted forensics models, for AI-generated-media detection — already the policy Phase 3 followed for images. Phase 5 extended the exact same interface pattern to audio (`AudioForensicsProvider`) and video (`VideoForensicsProvider`); Phase "B/C-real" investigated real self-serve providers and built a genuine client.
**Status: LOCKED (approach) — a real provider client exists (Resemble AI Detect, `app/integrations/media_forensics_client.py`), kept OPT-IN and NOT activated by default, on the user's explicit, confirmed cost decision.** Provider comparison: Pindrop and Sensity AI are enterprise-sales-only with **no self-serve path at all** (ruled out entirely, not a cost question — there's no way to self-onboard). Resemble AI Detect is the one option with a genuine no-contract self-serve tier and published third-party benchmark results (#1 on DFBench, 98.1% accuracy) — the most credible real candidate found, covering audio+video+image in one API. Its cost is real and non-trivial: **~$0.035/sec audio (~$2.10/min), ~$0.07/sec video (~$4.20/min)** on the entry Flex tier as of this writing — a 3-minute forwarded video would cost roughly $12.60 to forensics-check alone. `ResembleAudioForensicsProvider`/`ResembleVideoForensicsProvider` are real, correct clients (real auth, real multipart upload, real error-mapping, `zero_retention_mode=true` for privacy) — but **no real Resemble credentials exist in this environment**, so they've been tested only against a scripted `httpx.MockTransport` (`tests/unit/test_resemble_forensics_client.py`), never a live call. `NullAudioForensicsProvider`/`NullVideoForensicsProvider` remain the active defaults (`app/core/provider_selection.py`) — the WhatsApp reply still says "AI-generation detection unavailable" explicitly until real credentials are supplied and the spend is deliberately approved. Every audio/video-derived claim's media-authenticity check never gates classification, same as image forensics in Phase 3. **Response-schema caveat**: Resemble's exact JSON response field names couldn't be confirmed from public docs alone (their documentation site's deeper API-reference pages weren't fully accessible during research) — the response parser is deliberately defensive (recognized labels map directly; the provider's own confidence score is thresholded conservatively as a fallback; anything unrecognized reports `AUTHENTICITY_UNCERTAIN`, never a guess) but **must be validated against a real API response before being trusted in production**. **Still open**: (1) a real API call to confirm the response schema assumptions; (2) the cost/spend decision itself — activating this remains the user's call, not a default; (3) acceptable false-positive/negative tolerance is unchanged and still a product/legal judgment call; (4) a benchmark (reusing the existing `benchmark_datasets`/`benchmark_runs` shared infrastructure) is future work, same status as image forensics.

## Wall-clock processing timeout — undocumented gap, closed in Phase 5
decisions.md §12/§15 requires "a hard per-analysis wall-clock timeout, after which the analysis fails gracefully" — `MAX_PROCESSING_DURATION_SECONDS` has existed as a config placeholder since Phase 2 but was never actually enforced anywhere in the codebase until Phase 5.
**Status: LOCKED — now implemented and applied uniformly.** See `app/core/pipeline_timeout.py`, wired into every pipeline (Text/Image/Url/Audio/Video) via `app/webhook/whatsapp/router.py`, not just the new audio/video ones where a runaway frame-extraction/transcription job would matter most. A trip cancels mid-flight DB work cleanly (the analysis attempt simply never commits, per `app/db/session.py`'s `session_scope` rollback-on-exception semantics) and always resolves to a distinct, honest reply — never a silently dropped message. No open question remaining here.

## Phase 5 final validation audit — findings, and what remains blocked
A dedicated audit pass reviewed the STT/audio-forensics/video-forensics providers, credential handling, and configuration visibility, and attempted a real live validation.
**Status: Environment check confirmed no live validation is possible in this build — CODE COMPLETE, LIVE VALIDATION STILL BLOCKED.** Concretely verified during this audit (not just implemented, actually checked):
- **No `.env` file exists anywhere in the project, and none of `SPEECH_TO_TEXT_API_KEY`/`AUDIO_FORENSICS_API_KEY`/`VIDEO_FORENSICS_API_KEY` are set** — confirmed by direct inspection, without printing any value. No real audio/video sample files exist in the repository either.
- **API-key-leakage safety is now empirically proven, not just asserted.** `tests/unit/test_provider_credential_safety.py` captures real log output (via `caplog`) while exercising both providers' full failure surface (auth failure, timeout, malformed response, server error, an unexpected raw crash) with a realistic-looking secret value, and asserts it never appears in any log record. This also confirmed a pre-existing, correct safeguard: `logging.getLogger("httpx").setLevel(logging.WARNING)` (set since Phase 1) suppresses httpx's own verbose request/header logging, which could otherwise leak auth headers at DEBUG level.
- **A genuine parsing bug was found and fixed during this audit, with a regression test.** `_extract_label_and_score`'s fallback chain used `or` between optional numeric fields — a real score of `0.0` (a confident "not AI-generated" result) is falsy in Python and was silently skipped in favor of the next fallback field, or the conservative default. Fixed to explicit `None`-checks; `test_genuine_zero_score_is_never_silently_dropped` in `tests/unit/test_resemble_forensics_client.py` guards this.
- **A second, more specific Resemble response shape was found via follow-up research** (`payload["metrics"]`/`["video_metrics"]` containing `label`/`aggregated_score`/`score` as a possible array/`certainty`), distinct from the flatter shape originally assumed. The parser now tries both, in order — but Resemble's actual API-reference pages remain **inaccessible to automated fetching** (their docs site is JS-rendered; every direct sub-page URL tried either 404s or redirects to the docs root) even after repeated attempts with different URLs and search-engine-cached paths. **Neither shape has been confirmed against a real response** — this remains exactly as open as before the audit, just now hedged against two plausible shapes instead of one.
- **`GET /health` now reports real vs. Null provider state for all three** (`speech_to_text_provider`/`audio_forensics_provider`/`video_forensics_provider`), introspected from the actual `app.state` objects constructed at startup, not re-derived from config — verified by test to correctly read `"null"` by default and flip to `"real"` when credentials are set, independently per field.
- **Optional, credential-gated live tests now exist** (`tests/integration/{test_sarvam_stt_live,test_resemble_forensics_live}.py`, `tests/fixtures/live_samples/`) — excluded from the default suite, each skipping independently and honestly (never failing, never faking a result) when its required API key or real sample file is absent. As of this writing, every one of them skips — **zero live calls to Sarvam or Resemble have been made in this build's history**.
**Still open, unchanged by this audit**: everything the two entries above already listed — real credentials, a real API call to confirm the response schema, real Malayalam/Tamil/Hindi/English voice samples, a real known-authentic and known-synthetic audio/video sample pair, and the deliberate cost/spend decision to actually activate Resemble.

## Phase 6 dashboard API — findings, gaps, and what remains blocked
**Status: Backend REST API complete and tested against a real (SQLite) test database; WhatsApp OTP delivery NOT live-tested (no Meta credentials in this environment); three items deliberately not built, each disclosed rather than silently dropped.**

- **WhatsApp-OTP dashboard login is a confirmed, disclosed conflict with decisions.md §4** ("No proactive/scheduled messaging of any kind ships in the MVP"). OTP delivery is a genuinely proactive send — triggered the instant a user starts a dashboard login, not in reply to an inbound message — which in a real Meta deployment requires a pre-approved message template when the recipient is outside an active 24h conversation window (same precondition already established for "Check This Tomorrow", risk #4/#18). Built anyway per explicit user instruction (AskUserQuestion, Phase 6 planning); the code path itself (OTP generation/hashing/storage/expiry/attempt-limiting/JWT issuance) is fully implemented and tested against a fake WhatsApp sender — the ACTUAL Graph API call has never been made in this environment.
- **`POST /history/{id}/reopen`** (documented in api-design.md's route list) is **not implemented** — its semantics are undefined by any locked doc (no "reopen" concept in agent-architecture.md's History Manager contract, no cost/re-execution rule in decisions.md). Guessing an implementation risked exactly the "duplicate fact-checking logic" instruction this phase was told to avoid. See `app/api/v1/routers/history.py`'s module docstring.
- **A genuine conflict with database-schema.md's "Privacy Mode ↔ schema behavior" table was found and resolved with the user, not silently decided**: that table lists History as "Disabled" for Privacy Mode ON (the default for every new user). Confirmed resolution: History stays available to every user regardless of `privacy_mode` — the aggressive purge TTLs already make a privacy-mode user's history naturally near-empty within ~48h, and blocking the endpoint outright was judged to add no privacy benefit while breaking the ability to see a just-completed analysis. See `docs/database-schema.md`'s Phase 6 status note and `app/api/v1/routers/history.py`.
- **"Clear History" is a soft delete** (`analyses.is_deleted=true`), not the "on-demand hard delete via cascading FKs" the Privacy Mode table originally described for Privacy-Mode-OFF users — it reuses the `is_deleted`/`deleted_at` columns that already existed since Phase 2. The row is hard-deleted (with all children) once it reaches the retention purge's own age-based cutoff, same as any other analysis; user-initiated deletion currently only hides the row immediately rather than accelerating the hard purge.
- **Full account deletion (`data_deletion_requests`, `DELETE /account`) remains unbuilt** — explicitly excluded from Phase 6's confirmed scope, per the user's instruction not to add it unless the locked docs required it for this phase.
- **Explore, PDF Reports, Admin/Appeals, `/overview`, scheduled-checks, and `conversation_sessions` all remain unbuilt** — all explicitly excluded from Phase 6's confirmed scope (Explore/PDF Reports deferred to their already-locked V2 slot, per an earlier AskUserQuestion decision; the rest excluded outright per the user's instruction).
- **Retention purge deletes are explicit, ordered, child-to-parent SQL statements, deliberately NOT relying on `ON DELETE CASCADE` firing** — this project's SQLite test engine has never enabled `PRAGMA foreign_keys` (grepped, confirmed absent across every phase), so every FK's `ondelete="CASCADE"` is real on production Postgres but silently inert in this project's own test suite. Trusting CASCADE here would have made the purge code look correct in tests while its actual cascading behavior stayed unverified — the opposite of what "Tests MUST prove cascading relationships work" requires. `app/agent/retention.py` deletes each child table explicitly instead, verified by `tests/integration/test_retention_purge.py` against a real SQLite database (expired-vs-non-expired, cross-user isolation, idempotent re-runs, full parent+child trees provably gone with nothing orphaned).
- **Hindi/Tamil (`hi`/`ta`) remain selectable-but-not-rendered**, unchanged since Phase 2: `users.preferred_language` accepts all 4 documented codes, but `app/i18n/templates.py`'s `SUPPORTED_LANGUAGES` still only covers `en`/`ml`. The Settings API (`GET/PUT /settings/language`) is honest about this — its response includes `translated_replies_available`, `false` for `hi`/`ta` — rather than silently claiming full support to make the endpoint look complete.
- **JWT revocation-check failures (a Redis outage) fail CLOSED**, by direct analogy to `app/agent/safety_gate.py`'s existing "ERROR is treated as do-not-proceed" precedent — a design decision made for this phase, not specified by any locked doc, documented in `app/api/v1/deps.py`.

## Phase 7 security/production hardening — findings, and what remains outside engineering scope
**Status: Engineering hardening complete and tested (547 passed, 12 deselected, 0 regressions); the full decisions.md §15 release gate is NOT complete — three items are legal reviews, not code, and remain genuinely blocked regardless of engineering effort.**

- **A real, previously-unimplemented locked requirement was found and closed**: decisions.md §12/§15 require rate limiting on every route, "per-user for authenticated routes, per-IP for public ones" — Phase 6 built the entire dashboard API with zero rate limiting. Closed by reusing Phase 1's `RateLimiter` (`app/core/rate_limit.py`) unchanged: per-user on every authenticated `/api/v1/*` route (enforced once, in `get_current_token_payload`, so every route inherits it automatically rather than each route remembering its own `Depends()`), and per-IP on `POST /auth/link/start` specifically — the latter closes a real cost-control gap, not just an abuse one: without it, an attacker cycling through many different phone numbers (each with its own independent per-phone cooldown) could trigger unlimited real WhatsApp-send attempts, each a genuine per-message cost in a credentialed production deployment.
- **Response security headers and a request-size ceiling were added** (`app/core/http_hardening.py`) — `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` on every response; `Cache-Control: no-store` and a `Content-Length`-based 413 ceiling on `/api/v1/*` specifically. **Honest limitation**: the size ceiling checks the declared `Content-Length` header only — a request sent with `Transfer-Encoding: chunked` and no `Content-Length` bypasses this specific check (uvicorn/Starlette still buffer the full body into memory regardless, so this is a real, disclosed gap in the defense, not a false sense of complete protection). No CORS middleware was added — a deliberate decision, not an oversight: this backend has no frontend (confirmed scope decision), so the browser's default same-origin restriction is already the correct, secure posture; adding a permissive CORS policy now would be a regression, not hardening.
- **An endpoint inventory test now exists** (`tests/unit/test_endpoint_inventory.py`) that walks the live OpenAPI schema and fails the suite if any `/api/v1/*` route ships without `HTTPBearer` security, or if an unexpected new route appears — this is a regression guard against a *future* route accidentally shipping unauthenticated, not just a one-time manual audit.
- **Everything else on decisions.md §15's checklist was already built and tested in Phases 1-6, re-confirmed here, not re-implemented**: webhook signature verification + replay/idempotency protection (Phase 1), SSRF protection including per-redirect-hop checking (Phase 4), prompt-injection defenses (delimited untrusted-content blocks, Phase 2/5b), file/media validation (magic-byte sniffing, decompression-bomb guards, duration/size caps — Phases 3/5), JWT/OTP authentication and cross-user authorization (Phase 6), secrets-never-logged (Phases 1/5/6's dedicated credential-safety test suites).

## Phase 10 — Final Release & Verification: three real bugs found and fixed
**Status: Final audits complete. 709 passed, 12 deselected, 0 failed. Three genuine, previously-undetected bugs were found by doing the verification work for real rather than assuming prior phases' green test runs were sufficient — all three fixed, one with a new regression test.**

The most valuable finding of this phase is that **a fully green test suite was hiding a real production-breaking bug**, precisely because every test in it uses test doubles for the two pieces of infrastructure the bug lived in:

1. **`app/core/rate_limit.py` had NO Redis-outage handling at all** — a Redis `ConnectionError` propagated straight out of `check_and_increment` into an unhandled HTTP 500, across all six of its call sites (webhook per-sender, OTP-start per-IP, dashboard per-user, admin per-admin, admin-login per-IP, Explore per-IP). **Invisible to all 708 tests passing at the time**, because the entire suite uses `fakeredis`, which never simulates a connection failure. Caught by Phase 10's real uvicorn boot smoke test: `GET /api/v1/explore/claims` returned 500 against a genuinely unreachable Redis. **Fixed to fail OPEN** — a deliberate, documented choice that differs from `app/api/v1/deps.py`'s JWT-revocation check (which fails CLOSED): rate limiting is abuse/cost protection, not security-critical access control, and taking every route down because the rate limiter's backing store hiccupped is strictly worse than briefly serving unthrottled. Covered by a new regression test (`test_redis_outage_fails_open_not_with_an_unhandled_exception`) using a minimal broken-Redis stand-in, since `fakeredis` structurally cannot reproduce this.
2. **`infra/docker-compose.yml`'s `api` service never had `DATABASE_URL` or a `postgres` dependency wired** — a Phase 1 leftover ("Phase 1 does not use Postgres yet") that was never revisited after Phase 2 added real database use. Inside the container's own network namespace, `Settings`' `localhost:5432` default resolves to the `api` container itself, not the `postgres` service — so the app as containerized has never been able to reach its own database. Fixed (correct service-name hostnames, `depends_on` both services' healthchecks).
3. **`infra/docker/Dockerfile.api` never copied `alembic.ini`/`migrations/` into the image** — meaning `alembic upgrade head` could never actually be run from inside the container, only from a host checkout. Fixed.

**All three are the same class of bug**: real infrastructure paths that no automated test in this project could ever have exercised, because the tests deliberately (and correctly) use SQLite + `fakeredis` + no containers. They are exactly what the "boot the REAL application" and "prepare production configuration" steps exist to catch, and finding them is a direct argument for running the real-infrastructure validation still listed as blocked in §9.7/§9.8 above before any production deployment — **the remaining blocked items are not a formality; this phase demonstrated empirically that real-infrastructure verification finds real bugs that a green test suite does not.**

### Phase 10 §9.10 — load testing (performed) and one measured non-finding

A controlled load test was run against the live server, deliberately restricted to endpoints whose measured path makes no paid third-party API call. **1,050 requests, 0 errors, 0 5xx.** Single uvicorn worker, SQLite, dev laptop — **these are not production numbers**, and a real Postgres/multi-worker deployment would behave differently:

| Endpoint | n | concurrency | req/s | p50 | p95 | p99 |
|---|---|---|---|---|---|---|
| `GET /health` | 200 | 20 | 167 | 109ms | 180ms | 250ms |
| `GET /api/v1/history` | 200 | 20 | 60 | 320ms | 389ms | 542ms |
| `GET /api/v1/overview` | 200 | 20 | 45 | 433ms | 564ms | 655ms |
| `GET /api/v1/explore/claims` | 200 | 20 | 86 | 230ms | 273ms | 344ms |
| `GET /api/v1/notifications` | 200 | 20 | 59 | 336ms | 438ms | 487ms |
| `GET /history/{id}/report.pdf` | 50 | 10 | 25 | 308ms | 1267ms | 1603ms |

Memory grew ~12MB across the run (166MB → 178MB) with no sign of a leak.

**Rate limiting demonstrably works under real concurrent load** — the first run returned 429s at exactly the configured per-user/per-IP thresholds; the table above was re-measured with the limits raised via their existing config knobs (no code change).

**The one apparent bottleneck, and the fix that was measured and then REVERTED**: PDF generation showed p95 1.2s / p99 1.7s — the classic signature of blocking CPU work on the event loop (fpdf2's font subsetting and rendering are synchronous). The textbook fix, `starlette.concurrency.run_in_threadpool`, was implemented and A/B measured. **It produced no improvement at all**: a dedicated cross-talk test (how much `/health` degrades while 8 concurrent PDF generations are in flight) measured an identical **3.84x** degradation both with and without it, and the PDF endpoint's own percentiles were unchanged within noise. The cause is CPython's GIL — fpdf2 is pure Python, so a worker thread contends for the same lock and nothing runs in parallel. **The change was reverted rather than kept as unhelpful indirection**, and the measurement is recorded in `app/agent/pdf_report.py`'s docstring so it isn't re-investigated later. The real mitigation is process-level (multiple uvicorn workers/replicas), with the caveat that the three in-process periodic jobs must then be pinned to one replica — documented in `docs/production-deployment.md` §5. **No other bottleneck was found that warranted a code change.**

**Final security audit**: no SQL injection surface (every query is SQLAlchemy-parameterized; the only two raw-SQL uses are static `SELECT 1` health probes), no secrets in the repository, no unauthenticated `/api/v1/*` route except the four deliberately-public ones (OTP start/verify, Explore, admin login — enforced by `tests/unit/test_endpoint_inventory.py` against the live OpenAPI schema), every Phase 7 control confirmed still in place and untouched.
