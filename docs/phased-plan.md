# SathyaScan — Phased Development Plan

Scope boundaries follow the PRD's own MVP/V2/V3/V4 split (§40-43); phases below decompose the **MVP** into sequential, independently verifiable milestones, since the PRD gives the target feature set but not a build order.

**Locked decisions affecting this plan are in [`decisions.md`](decisions.md).** Three changes from the original plan: (1) "Check This Tomorrow" is removed from V2's default scope and now has explicit preconditions (decisions.md §4/§14) before it can even be scheduled; (2) a safety-gate design step is pulled forward to precede Phase 3's media pipeline, since the gate must exist architecturally before any media analysis code runs — its full implementation remains blocked on legal review regardless of when engineering builds the slot for it; (3) **audio (originally V2) and video (originally V3) analysis were explicitly reprioritized ahead of Dashboard/History/Privacy Mode/Multilingual and Hardening**, at the user's direct instruction, given as **Phase 5** on 2026-08-14 — this is a confirmed, deliberate reordering, not a silent rewrite. The rest of this document's phase numbers are shifted down by one to accommodate it (the original Phase 5 is now Phase 6, original Phase 6 is now Phase 7, and V2/V3 lose the bullets that moved into Phase 5). See the note at the end of the sequencing rationale for the tradeoffs this reordering accepts.

## Sequencing rationale

- Text-only first (Phase 2) validates the hardest new capability — evidence-first claim verification — before adding media-processing complexity on top. The budget guard and circuit breaker are built here, not bolted on later, because Phase 2 is the first code path that spends money on searches/LLM calls at all.
- The safety-gate **interface** moves to the front of Phase 3, ahead of any actual media-analysis tool, because the architecture must never have a code path where media reaches an analyzer before passing through the gate — building the slot early makes that invariant true from the first media-handling commit, even though the gate's real implementation (vendor, reporting procedure) stays blocked on legal review regardless of engineering timeline.
- Image/OCR (Phase 3) comes before URL (Phase 4) because screenshots (PRD §12) explicitly reuse OCR, and OCR's Indic-language accuracy is a real risk needing a benchmark — not an assumption — before the engine is locked in.
- **Audio/Video (Phase 5) was pulled forward from its original V2/V3 position, ahead of Dashboard/Privacy Mode/Multilingual (now Phase 6) and Hardening (now Phase 7), at the user's explicit instruction on 2026-08-14.** This is a deliberate reprioritization, not a discovery that the original order was wrong — the original rationale for building Dashboard/Privacy-Mode-verification and the full security review *before* adding new attack surface (arbitrary user-submitted audio/video, now PyAV-decoded) still holds and is recorded here for whoever picks up Phase 6/7 next: Privacy Mode's retention/deletion verification is now gating a system with MORE persisted media-derived data than when that phase was originally scoped (`transcripts`, `video_frames`), and the Phase 7 security checklist now has two new decode-heavy media paths (audio validation, video frame/audio-track extraction) to include that didn't exist when the original checklist was drafted.
- Dashboard/History/Privacy Mode/Multilingual are bundled into one phase (now 6) because they're all "make the already-working pipeline properly usable and compliant" work, not new AI capability — and Privacy Mode specifically needs the full analysis pipeline already in place to have real data whose retention it's actually gating, and now specifically needs a verification step proving deletion actually happens.
- Hardening (now Phase 7) is deliberately last and explicitly gates launch — abuse handling and the security review are treated as launch-blocking, not nice-to-haves, because MVP already exposes a public inbound WhatsApp surface accepting arbitrary user media (now including audio/video). Phase 7 is technical readiness only; the three legal reviews (illegal content, DPDP, defamation policy) are a separate, non-engineering gate on top of it.
- Scheduled re-checks are pulled out of the default V2 timeline entirely (phase 8a) rather than left inside "V2" where it would silently imply it's next-in-line work — its start date is undefined until its three preconditions are met, which may take longer than the rest of V2.
