# SathyaScan Backend — Phase 1 through Phase 9

WhatsApp integration foundation (Phase 1), text fact-checking pipeline (Phase 2), safety gate + image/OCR pipeline (Phase 3), URL Analyzer + URL Safety Module (Phase 4), audio + video transcription/OCR fact-checking (Phase 5, reprioritized ahead of Dashboard/Hardening at the user's explicit instruction — see `docs/phased-plan.md`'s reprioritization note), a JWT-authenticated dashboard REST API (Phase 6 — backend only, no frontend, confirmed scope decision), security/production hardening (Phase 7), full backend features (Phase 8 — Explore, PDF reports, "Check This Tomorrow" scheduling backend, full account deletion, analytics/overview, conversation sessions, expanded search/filtering, notifications), a Hindi/Tamil localization + Unicode PDF rendering hardening pass, and Production Completion & Trust (Phase 9 — admin system, appeals, moderation, provider/job monitoring, account suspension). Still backend-only, no frontend — a confirmed, locked scope decision, not a gap — see [`docs/phased-plan.md`](../docs/phased-plan.md) and [`docs/decisions.md`](../docs/decisions.md). **Public launch still requires the three mandatory legal reviews (decisions.md §5/§6/§9), a load test, a staging soak, a real WhatsApp-credentialed OTP live-test, AND the three preconditions for proactive WhatsApp sending (decisions.md §4/§14) — none of which are engineering-completable in this environment; see the Phase 9 section below and `docs/production-deployment.md`.**

## What's implemented

**Phase 1** — webhook verification, signature checking, idempotency, safe message parsing, per-user rate limiting.

**Phase 2** — text messages are routed through a real pipeline: claim extraction → bounded evidence-gathering (Claude with exactly one callable tool, `search_evidence`) → deterministic source-credibility lookup → evidence synthesis → a **deterministic classification guard** that independently verifies the evidence actually supports whatever Claude suggested, overriding it if not → multilingual (English/Malayalam) WhatsApp reply. PostgreSQL persistence, a daily spend circuit breaker, global concurrency limiting, and same-user duplicate-content reuse are all in place.

**Phase 3** — image messages are routed through: secure, SSRF-protected download from Meta (no redirects, size-capped, resolved-IP checked before every fetch) → real content validation (magic-byte sniffing, decompression-bomb guard — never trusts the claimed MIME type or extension) → a **non-bypassable, fail-closed safety gate** → OCR → the OCR'd text is fed through the *exact same* Phase 2 claim/evidence/classification pipeline (code-shared, not duplicated — see `app/agent/claim_pipeline_shared.py`). **No blob storage exists in Phase 3** — media is downloaded to memory and discarded after processing, never written to disk. **Two components are interfaces-only in this build**: the safety-gate provider and the OCR engine are both `Null*` stubs — no CSAM/content-safety vendor and no benchmarked OCR engine are wired (see `docs/risks-and-open-questions.md` for why, and `docs/decisions.md` §6/§11 for the locked policy this follows). AI-generated-image detection is also stub-only (`NullImageForensicsProvider`) — a confirmed scope decision to avoid an unnecessary new paid API this phase.

**Phase 4** — a WhatsApp text message whose entire body is a single URL is routed to the URL Analyzer + URL Safety pipeline instead of plain claim extraction (`app/agent/url_detection.py`; a URL mentioned alongside other text still goes through the Phase 2 text path, unchanged). Flow: SSRF pre-check on the URL's host → robots.txt check (decisions.md §3) → ONE SSRF-protected fetch (`app/web/fetcher.py` — **every redirect hop is re-checked against private/internal IP ranges, not just the first URL**, a deliberate policy difference from Phase 3's media downloader, which refuses all redirects outright since general web URLs redirect constantly) → HTML content extraction (title/article-text/publisher/date) → URL Safety heuristics (HTTPS, domain pattern/typosquat detection, redirect-chain analysis, phishing keywords, fake-login-form detection — all deterministic, no LLM calls, no credentials) plus real WHOIS-based domain-age lookup (`app/web/domain_age.py` — no credentials needed, WHOIS is unauthenticated; confirmed with a live lookup during implementation) → the extracted article text is fed through the *exact same* Phase 2/3 claim/evidence/classification pipeline. **Unlike Phase 3, most of Phase 4 is wired for real, not stubbed** — the fetcher, robots.txt check, HTML extraction, and domain-age checker all need zero credentials. **Only the optional Safe Browsing-style threat-intel check is a `Null*` stub** (`NullThreatIntelProvider`) — explicitly marked optional in `docs/phased-plan.md`'s Phase 4 scope, blocked purely on a paid API subscription this environment doesn't have. Every WhatsApp reply for a URL always includes a distinct safety-risk block (even when the fetch itself failed, was SSRF-blocked, or was disallowed by robots.txt — a real, useful safety result either way) alongside the credibility assessment when claims were found. The URL itself, never the fetched page content, is what's persisted to `analyses.input_text` (decisions.md §3's no-full-text-storage principle, applied here the same way Phase 3 never persists raw media bytes).

**Phase 5a (audio)** — voice notes/audio files: SSRF-protected download (a separate, appropriately-sized `MetaMediaClient` instance — 25MB vs image's 10MB) → real magic-byte + PyAV duration validation (`app/media/audio_validation.py`, supports OGG/MP3/MP4/AAC/AMR/WAV) → the **same** non-bypassable safety gate → Speech-to-Text (budget-guarded, same counter as every other pipeline) → the transcript is fed through the *exact same* Phase 2/3 claim/evidence/classification pipeline, **never translated first** — it stays in its original spoken language (Malayalam/Tamil/Hindi/English all genuinely supported by the interface, confirmed with scripted fixtures for all four) — → an **independent, best-effort** audio-forensics check that never gates the fact-check verdict and is always shown as a separate WhatsApp block. The transcript is durably persisted (`transcripts` table, migrated this phase) for auditability, per the user's explicit requirement; `analyses.input_text` stays empty (no duplication). On transcription failure, the reply is `insufficient_evidence` with a dedicated message — never a guessed verdict.

**Phase 5b (video)** — videos: SSRF-protected download (a third `MetaMediaClient` instance, 100MB limit) → magic-byte + PyAV duration/resolution validation (`app/media/video_validation.py`) → the same safety gate → **real, bounded key-frame extraction** (`app/media/frame_extractor.py` — hard caps on frame count and sampling interval, PyAV-based, never decodes more frames than the configured ceiling even on a much longer video, confirmed by test) → each frame OCR'd via the **exact same** `OCRTool` Phase 3 built (no second OCR engine) → **real audio-track extraction + transcode to WAV** (`app/media/audio_extractor.py`, credential-free) → Speech-to-Text, reusing the exact same `STTTool` Phase 5a built → **deterministic multimodal fusion** (`app/agent/multimodal_fusion.py`) structures spoken + on-screen content into one document — mechanically deduping identical consecutive on-screen captions, but never re-implementing claim-level deduplication (that stays the existing `ClaimExtractionTool`'s judgment call) — → the fused document goes through the *exact same* Phase 2/3 claim pipeline → an **independent** video-forensics check. If one modality is missing (silent video, or STT/OCR unavailable), the analysis proceeds on whatever the other modality found — a missing modality is never silently treated as "nothing to check" as long as the other one has something. **Frame images and raw audio/video bytes are never persisted** — only extracted text, per-frame timestamp/language/confidence (`video_frames`, a new table this phase) and the transcript (`transcripts`, shared with Phase 5a). **Frame extraction and audio-track extraction are real** (PyAV, a self-contained ~28MB wheel bundling FFmpeg, no system install needed, no credentials).

**Phase A/B/C-real (real providers, opt-in)** — three genuine, correct provider implementations now exist behind the SAME interfaces above, selected via `app/core/provider_selection.py`, but **none is activated by default**:
- **Speech-to-Text**: `SarvamSpeechToTextProvider` (`app/integrations/speech_to_text_client.py`) — selected after comparing against Google Cloud Speech-to-Text (Sarvam is ~2-3x cheaper, purpose-built for Malayalam/Tamil/Hindi/English with code-mixing support). Set `SPEECH_TO_TEXT_PROVIDER=sarvam` + `SPEECH_TO_TEXT_API_KEY` to activate; otherwise `NullSpeechToTextProvider` stays active.
- **Audio/video forensics**: `ResembleAudioForensicsProvider`/`ResembleVideoForensicsProvider` (`app/integrations/media_forensics_client.py`, shared implementation) — Resemble AI Detect was the only self-serve, no-contract option found (Pindrop/Sensity are enterprise-sales-only). **Real, non-trivial per-unit cost** (~$0.035/sec audio, ~$0.07/sec video on the entry tier) — kept opt-in as a deliberate, confirmed decision, not a default-on spend. Set `AUDIO_FORENSICS_PROVIDER=resemble`/`VIDEO_FORENSICS_PROVIDER=resemble` + the matching `_API_KEY` to activate.

**None of these three real providers has been tested against a live API** — no credentials exist in this environment. Each is tested against its *real* request-construction/response-parsing logic via a scripted `httpx.MockTransport` (`tests/unit/test_sarvam_stt_client.py`, `tests/unit/test_resemble_forensics_client.py`), same rigor as the media downloader/URL fetcher, but this is not equivalent to a live-credentialed test or a decisions.md §11 benchmark — see `docs/risks-and-open-questions.md` for the full, honest status of each.

**New in Phase 5, applied to every pipeline (not just audio/video)**: `MAX_PROCESSING_DURATION_SECONDS` — a hard wall-clock timeout (decisions.md §12/§15) that existed as a config placeholder since Phase 2 but was never actually enforced until now (`app/core/pipeline_timeout.py`).

**Phase 6 (dashboard REST API, backend only — no frontend, a confirmed scope decision)** — everything under `/api/v1`, JWT-authenticated except the auth endpoints themselves:

- **Auth** (`app/api/v1/routers/auth.py`) — WhatsApp-OTP dashboard login: `POST /auth/link/start` (generates a cryptographically secure 6-digit code via `secrets.randbelow`, hashes it with the same keyed-HMAC pattern `hash_phone_number` already uses, stores it with a 5-minute expiry, sends it via the existing `WhatsAppSender`), `POST /auth/link/verify` (single-use, attempt-limited, identical generic error for every failure mode so the endpoint can't be used to enumerate registered phone numbers), `POST /auth/refresh` (re-validates the current token and rotates it — the old token is immediately revoked), `POST /auth/logout` (real, server-enforced revocation via Redis, not just "the client discards the token"). **A confirmed, disclosed conflict with decisions.md §4** ("No proactive/scheduled messaging... ships in the MVP"): OTP delivery is a genuinely proactive send outside any inbound conversation window, which needs a pre-approved Meta message template in a real deployment — built anyway per explicit user instruction, with the limitation documented in the module's own docstring, not silently worked around.
- **JWT infrastructure** (`app/core/jwt_auth.py`) — HS256, `PyJWT`, Redis-backed revocation-by-`jti` (TTL = the token's own remaining lifetime, so the revocation set never grows unboundedly). A Redis outage during a revocation check **fails closed** (401/503, never silently treated as "not revoked") — a direct analogy to `app/agent/safety_gate.py`'s existing fail-closed precedent, extended from content-safety to auth.
- **History** (`app/api/v1/routers/history.py`) — `GET /history` (filters: `type`, `result`, `from`/`to`, `q` free-text search over the user's own `input_text`, paginated), `GET /history/{id}`, `DELETE /history/{id}`, `DELETE /history`. Every query is scoped to the JWT's `user_id`, never a client-supplied one; requesting another user's `analysis_id` returns 404, not 403 (a 403 would confirm the row exists and belongs to someone else). Reuses `app.agent.claim_pipeline_shared.load_verdicts` for claims+evidence assembly — no second fact-checking/query layer. **`POST /history/{id}/reopen` is not implemented** — its semantics are undefined by any locked doc; see the module's docstring.
- **Settings** (`app/api/v1/routers/settings.py`) — `GET/PUT /settings/language` (accepts all 4 documented codes `ml/en/hi/ta`; `translated_replies_available` reports `true` for all four — see the Phase 8 hardening section below for the fix that closed the earlier hi/ta gap), `GET/PUT /settings/privacy`.
- **Privacy Mode retention purge** (`app/agent/retention.py`) — a real, config-driven purge, run by a lightweight in-process asyncio periodic task (`main.py`'s lifespan, NOT Celery — matches every prior phase's BackgroundTasks-over-Celery precedent). Deletes are **explicit, ordered, child-to-parent SQL statements**, deliberately not relying on the database's `ON DELETE CASCADE` firing — this project's SQLite test engine never enables `PRAGMA foreign_keys`, so trusting CASCADE would have left the purge's cascading behavior unverified in the one place it needed proving. `media_attachments.retention_expires_at` is now populated at creation time by Image/Audio/VideoPipeline. Verified against a real (SQLite) test database — expired-vs-non-expired, cross-user isolation, idempotent re-runs, full parent+child trees provably gone with nothing orphaned (`tests/integration/test_retention_purge.py`).
- **Audit log** (`app/agent/audit.py`, `app/models/audit_log.py`) — decisions.md §9's "required, not optional, MVP component", never built until now. Records OTP requests/verifications/failures, logins, token refresh/logout, settings changes, history deletions. `write_audit_log` defensively **raises** (not silently strips) if a caller ever attempts to include an OTP code, JWT, password, or phone number/hash in its metadata.
- **A genuine conflict with database-schema.md's Privacy Mode table was found and resolved with the user, not silently decided**: that table lists History as "Disabled" for Privacy Mode ON. Confirmed resolution: History stays available to every user regardless of `privacy_mode` — see `docs/database-schema.md`'s Phase 6 status note.

**Explicitly excluded from Phase 6** (per the user's confirmed scope instructions at the time): Explore, PDF Reports, Admin/Appeals, `GET /overview`, scheduled-checks, `conversation_sessions`, full account deletion. **All except Admin/Appeals were subsequently built in Phase 8 — see below.**

**Phase 7 (security/production hardening)** — closes a real, previously-unimplemented locked requirement plus a handful of cheap, concrete hardening wins:

- **Dashboard API rate limiting** (decisions.md §12/§15, never implemented in Phase 6) — per-user on every authenticated `/api/v1/*` route (`app/api/v1/deps.py::get_current_token_payload`, so every protected route inherits it from the one dependency they all share, not a per-route opt-in), per-IP on the pre-auth `POST /auth/link/start` (bounds real WhatsApp-send cost exposure — without it, an attacker cycling through different phone numbers could trigger unlimited real message sends, each a genuine per-message cost in production, since each phone number's own cooldown is independent). Reuses `app/core/rate_limit.py::RateLimiter` unchanged — the exact mechanism Phase 1 built for the webhook.
- **HTTP hardening middleware** (`app/core/http_hardening.py`) — `SecurityHeadersMiddleware` (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` on every response; `Cache-Control: no-store` on `/api/v1/*`) and `RequestSizeLimitMiddleware` (413 on an oversized `Content-Length` for `/api/v1/*`). **Honest limitation**: the size check reads the declared `Content-Length` header only — a chunked-transfer-encoded request without that header is not caught by this specific check (uvicorn/Starlette still buffer it into memory regardless). No CORS middleware is added anywhere — deliberate, not an oversight: there is no frontend (confirmed scope decision), so the browser's default same-origin restriction is already correct; a permissive CORS policy would be a regression.
- **`/health` extended** with `phone_hash_pepper_configured`/`phone_encryption_key_configured`, alongside the existing `jwt_configured`/`safety_gate_provider_configured` — the same "silent fail-closed, so surface it" reasoning: an empty `PHONE_HASH_PEPPER` or `PHONE_ENCRYPTION_KEY` makes user creation/lookup fail for every single message, and previously had no single endpoint that would tell you that before it happened in production.
- **A live endpoint-inventory regression test** (`tests/unit/test_endpoint_inventory.py`) walks the real OpenAPI schema and fails the suite if any `/api/v1/*` route ships without `HTTPBearer` security, or an unexpected new route appears — a guard against a *future* route accidentally shipping unauthenticated, not a one-time audit.
- **Everything else on decisions.md §15's security checklist was already built and tested in Phases 1-6** (webhook signature/replay protection, SSRF including per-redirect-hop checks, prompt-injection defenses, file/media validation, JWT/OTP auth, cross-user authorization, secrets-never-logged) — re-confirmed present and passing, not rebuilt.
- **A known, disclosed, NOT-fixed limitation**: `POST /auth/link/verify`'s attempt-counter increment is not atomic — under true concurrent connections (real Postgres; this project's SQLite test setup cannot reproduce the race at all) two simultaneous requests bearing the same correct code could theoretically both succeed. Low severity (exploiting it requires already knowing the correct code) and not fixed here since the test infrastructure available can't actually prove a fix either way — see `docs/risks-and-open-questions.md`'s Phase 7 entry.
- **Explicitly NOT completed by this phase, and not code-completable in this environment**: a load test, a 48-hour staging soak, and the three mandatory legal reviews (decisions.md §5 defamation/classification liability, §6 illegal/CSAM content, §9 DPDP/privacy) — these remain **hard, unconditional blocks on public launch** regardless of engineering completeness; decisions.md is explicit that "no engineering decision in this document substitutes for #5, #6, or #9."

**Phase 8 (full backend features)** — still backend-only (confirmed scope decision, see the user's "PHASE 8 EXECUTION DECISIONS" message):

- **Explore** (`app/api/v1/routers/explore.py`) — `GET /explore/claims` (filters: `category`, `credibility_status`, `language`, `q`; `sort=trending|recent`; pagination), `GET /explore/categories`, `GET /explore/claims/{id}`. **No auth anywhere in this router, deliberately** — reads only from `explore_claim_clusters`, a table with **no FK column to `users`/`analyses` at all**, so the "Explore can never leak per-user data" guarantee is structural (no column to join on), not just a query-scoping convention. Populated by a periodic asyncio rollup (`app/agent/explore_rollup.py`, privacy-mode-excluded claims only), clustering by exact `compute_fingerprint` match (reusing Phase 6's duplicate-detection fingerprinting) — near-duplicate phrasing of the same claim is NOT fuzzy-merged in this build. Per-IP rate limited, same `RateLimiter` every other rate limit in this codebase uses.
- **PDF reports** (`app/agent/pdf_report.py`, `GET /history/{id}/report.pdf`) — generated on demand via `fpdf2` (pure-Python, no system deps) and streamed directly in the response, never written to disk. Labels are multilingual (`PDF_REPORT_STRINGS`, all 4 documented languages — see the Phase 8 hardening section below for real Unicode rendering).
- **"Check This Tomorrow" backend** (`app/models/scheduled_check.py`, `app/api/v1/routers/scheduled_checks.py`, `app/agent/scheduled_check_runner.py`) — `POST/GET/DELETE /scheduled-checks`, `.../retry`, duplicate-scheduling prevention. A periodic asyncio job re-runs the SAME `investigate_claim` function a fresh analysis uses (no second fact-checking system), diffs previous-vs-new result, detects a credibility change, and records execution status with bounded retries. `source_analysis_id` is `SET NULL` (not `CASCADE`) so a scheduled check outlives its source analysis being purged by Privacy Mode. **The proactive WhatsApp send itself is still blocked** — see below.
- **Notifications** (`app/models/notification.py`, `app/agent/notifications.py`, `app/api/v1/routers/notifications.py`) — `GET /notifications` (unread filter + count), mark-one-read, mark-all-read. `in_app` notifications deliver immediately; `channel='whatsapp'` rows are created and queryable but **always** written with `delivery_status='blocked_by_policy'` — `app/agent/notifications.py` never invokes the WhatsApp sender, per decisions.md §4/§14's still-unmet three preconditions (Meta requirements, template approval, cost budget). This is the same disclosed-conflict pattern Phase 6 used for WhatsApp-OTP delivery, applied consistently rather than silently deciding differently this time.
- **Full account deletion** (`app/agent/account_deletion.py`, `DELETE /account`) — exact `"DELETE"` confirmation-phrase gate (not a second OTP round-trip). Writes an `audit_log` entry before anonymizing, explicitly deletes every owned row (reusing Phase 6's `retention.py` helper functions), then anonymizes rather than deletes the `users` row (`phone_number_hash`/`phone_number_encrypted` re-derived from a fresh random UUID, `is_deleted=True`). Setting `is_deleted=True` immediately invalidates every outstanding JWT on its next authenticated request via the pre-existing `get_current_user` check — no separate token-revocation sweep needed.
- **Analytics/Overview** (`app/api/v1/routers/overview.py`) — `GET /overview`, strictly `Analysis.user_id == caller.id`-scoped, on a structurally different query path than Explore (api-design.md's "must never share a query path" rule).
- **Conversation sessions** (`app/models/analysis_session.py`, `app/api/v1/routers/analysis_sessions.py`) — `analysis_sessions` CRUD; deleting a session unlinks (not cascades) its member analyses.
- **Search/filtering** — History gained `language` + `sort=newest|oldest` filters, on top of its existing type/result/date-range/q/pagination; Explore already had category/credibility_status/language/q/sort/pagination from its initial build.
- **103 new Phase 8 tests, 0 regressions against Phases 1-7 (642 passed total, 12 deselected).**

**Phase 8 hardening (Hindi/Tamil localization + Unicode PDF rendering)** — closes the two known limitations flagged in Phase 8's own closing report, per an explicit follow-up instruction to fix only those two, with no architecture change, no frontend, and no new features:

- **Hindi/Tamil localization**: `app.i18n.templates.SUPPORTED_LANGUAGES` now covers all 4 documented codes (`en`/`ml`/`hi`/`ta`). Every string dict in that module (WhatsApp reply labels, URL-safety findings, media-forensics labels, notification text, PDF report labels) gained real Hindi and Tamil translations — a pure data change, since every caller already used a generic `dict.get(resolve_language(language), dict["en"])` pattern that transparently picks up new languages. `GET/PUT /settings/language`'s `translated_replies_available` now correctly reports `true` for `hi`/`ta` too, with no code change to that function (it was already computed generically from `SUPPORTED_LANGUAGES`).
- **Unicode PDF rendering**: `app/agent/pdf_report.py` now bundles three SIL Open Font License–licensed fonts (Noto Sans Malayalam/Devanagari/Tamil, static instances generated from Google's upstream variable fonts, under `app/assets/fonts/` — see that directory's `NOTICE.md`) and selects the correct one per `analysis.language` via fpdf2's `add_font()`. `en`-language reports are **unchanged** — still the original Helvetica core font, zero regression risk. `ml`/`hi`/`ta` reports now render real script glyphs, verified with genuine PDF text extraction (`pypdf`, a new test-only dependency) — claim text and labels round-trip back out as the exact original script, not `?`. The honest `?`-fallback safety net still exists for characters genuinely outside even the selected font's own repertoire (e.g. a stray third script mixed into a claim), proven by a dedicated mixed-script test — the fallback is narrowed to genuinely-missing glyphs, not removed.
- **4 new tests, 0 regressions (646 passed total, 12 deselected).** Migration cycle unaffected (no schema change). Real uvicorn boot + `/health`/`/openapi.json` re-verified.
- **Deliberately out of this fix's scope**: HTTPException error-detail strings remain English-only (a separate, pre-existing, disclosed boundary, not part of "the two known Phase 8 limitations" this fix targeted); these hi/ta translations are a first pass, not yet native-speaker reviewed — same caveat the original en/ml strings always carried.

**Phase 9 (Production Completion & Trust)** — admin system, appeals, moderation, provider/job monitoring, account suspension:

- **Admin system** (`app/models/admin_user.py`, `app/api/v1/routers/{admin_auth,admin}.py`) — `admin_users` is a SEPARATE identity table from `users` (email+password login via bcrypt, no public signup endpoint — created only via `python -m scripts.create_admin`, run locally with direct DB access). Strict RBAC: `role == "admin"` (user management, stats, system internals, audit-log) vs `"admin"|"moderator"` (appeals/moderation review), enforced by two distinct FastAPI dependencies, not a single shared check with a runtime branch. **Structural token-type separation**: `app/core/jwt_auth.py`'s tokens now carry a `token_type` claim (`"dashboard"` vs `"admin"`) — a dashboard token is rejected by every admin route and vice versa, proven by dedicated tests, even in the pathological case of a colliding UUID. `GET/POST /admin/users/*` (list/detail/suspend/reactivate), `GET /admin/stats/{users,analyses}`, `GET /admin/system/{health,jobs,providers}`, `GET /admin/audit-log`.
- **User suspension is functionally enforced, not just a DB flag** — checked in `app/api/v1/deps.py::get_current_user` (dashboard) and `app/webhook/whatsapp/router.py` (WhatsApp, a distinct decline reply in all 4 languages, never a silently dropped message).
- **Appeals** (`app/api/v1/routers/{appeals,admin_appeals}.py`) — user create/list/get/cancel-while-open, admin review with an explicit, tested state machine (`open → under_review/approved/rejected/escalated`, invalid transitions rejected with 400). Users can never directly modify a fact-check result through this API — approving an appeal records a decision, it never rewrites `analyses`/`claims`.
- **Moderation** (`app/api/v1/routers/{moderation,admin_moderation}.py`) — report spam/abuse/suspicious-content/malicious-URL (deliberately does NOT require owning the target) plus admin review. Reuses existing safety-gate/URL-safety infrastructure — no new AI moderation system was built.
- **Provider/job monitoring** (`app/core/provider_health.py`, `app/core/job_status.py`) — in-memory, per-process trackers (not a new metrics backend) wired into every `Tool` class's existing try/except, plus the three periodic background jobs. Never stores `str(exception)`, only the exception's class name. Exposed via `GET /admin/system/{providers,jobs}`.
- **62 new Phase 9 tests, 0 regressions (708 passed total, 12 deselected).** See `docs/risks-and-open-questions.md`'s Phase 9 entry for the full, honest status of what remains environment-blocked (real Postgres/Redis/provider credential validation, load testing) and `docs/production-deployment.md` for the production configuration guide.

## Local setup

```bash
cd backend
python -m venv .venv
source .venv/Scripts/activate   # Windows Git Bash; use .venv\Scripts\Activate.ps1 in PowerShell
pip install -r requirements-dev.txt
```

Copy the repo-root `.env.example` to `.env` and fill in WhatsApp + `ANTHROPIC_API_KEY` + `SEARCH_API_KEY` + `PHONE_ENCRYPTION_KEY` (generate one with `python -c "from app.core.encryption import generate_encryption_key as g; print(g())"`) + `PHONE_HASH_PEPPER`. **Phase 6**: also set `JWT_SECRET` (generate one with `python -c "import secrets; print(secrets.token_urlsafe(48))"`) — without it, every dashboard auth call fails closed rather than silently signing tokens with an empty secret (`GET /health`'s `jwt_configured` field reports this).

Start Postgres and Redis:

```bash
docker compose -f ../infra/docker-compose.yml up -d postgres redis
```

Run migrations:

```bash
cd backend
alembic upgrade head
```

Run the API:

```bash
uvicorn app.main:app --reload --port 8000
```


708 tests run by default, 12 deselected (425 through Phase 5 + 105 in Phase 6 + 17 in Phase 7 + 103 in Phase 8 + 4 in the Phase 8 hardening pass + 62 in Phase 9: admin auth/RBAC boundaries, user suspend/reactivate + dashboard/WhatsApp enforcement, appeals ownership/state-machine/duplicate-prevention, moderation reporting/review, provider-health/job-status trackers, structural admin/dashboard token-type separation), no external services required and no real network calls — Postgres is an in-memory SQLite database for tests, Redis is faked (`fakeredis`), and the Claude/search/WhatsApp/media/safety-gate/OCR/image-analysis/URL-fetch clients (plus the STT/audio-forensics/video-forensics fakes used by the pipeline-level tests) are all scripted fakes. Several components are tested against their *real* logic rather than fakes: the media downloader and the URL fetcher/robots-txt-checker (via `httpx.MockTransport`); audio/video validation, frame extraction, and audio-track extraction (via real PyAV-encoded fixtures, `tests/conftest.py`'s `make_sample_ogg_bytes`/`make_sample_mp4_bytes`, silent audio/blank video generated in-process, not canned byte strings); the real `SarvamSpeechToTextProvider`/`ResembleAudioForensicsProvider`/`ResembleVideoForensicsProvider` clients' request-construction and response-parsing logic (`tests/unit/test_sarvam_stt_client.py`, `tests/unit/test_resemble_forensics_client.py`, both via `httpx.MockTransport`); a dedicated proof that the pipelines integrate a real provider class through the exact same Protocol boundary the fakes use (`tests/integration/test_real_provider_pipeline_integration.py`); an empirical, captured-log-output proof that the Sarvam/Resemble API keys never appear in any log line across every failure path (auth failure, timeout, malformed response, server error, unexpected crash — `tests/unit/test_provider_credential_safety.py`); and — new in Phase 6 — the retention purge's cascading deletes run against a REAL (SQLite) test database rather than mocked query results, and the dashboard API's whole HTTP surface (auth/history/settings) is exercised end-to-end via `httpx.ASGITransport` over the real FastAPI app, not just unit-tested in isolation.

**Live-credentialed tests** (`tests/integration/{test_sarvam_stt_live,test_resemble_forensics_live}.py`, plus the pre-existing `test_domain_age.py` WHOIS test) are excluded from the default run (`pyproject.toml`'s `addopts = "-m 'not live_network'"`) and make **genuine, uncredentialed-by-default** calls to the real Sarvam AI / Resemble AI APIs. Run them explicitly with `pytest -m live_network`. Each one independently skips with an explicit, honest reason — never fails, never substitutes a mock and calls it live — when its required credential (`SPEECH_TO_TEXT_API_KEY` / `AUDIO_FORENSICS_API_KEY` / `VIDEO_FORENSICS_API_KEY`) or its real sample-media file (`tests/fixtures/live_samples/`, see that directory's README) is absent. **As of this writing, no real credentials exist in this environment, so none of these live provider tests has ever actually run against a real API** — only the credential-free WHOIS test has. Note Resemble's real per-second billing applies the moment its live tests are actually run with real credentials.

## Before any public exposure

`docs/decisions.md` §6 is a hard, unconditional gate: **the system must not be exposed publicly** until a real, legally-approved content-safety provider replaces `NullSafetyProvider`. Check `GET /health`'s `safety_gate_provider_configured` field — if `false`, this is still a stub deployment.

**Phase 6 additionally requires**: a real `JWT_SECRET`, `PHONE_HASH_PEPPER`, and `PHONE_ENCRYPTION_KEY` (`GET /health`'s three `*_configured` fields) before the dashboard/webhook is usable at all, and — separately, a real-world production precondition, not an engineering one — a pre-approved Meta message template before WhatsApp-OTP delivery works outside an active 24h conversation window (see `app/api/v1/routers/auth.py`'s module docstring and `docs/risks-and-open-questions.md`'s Phase 6 entry).

**Phase 7 additionally requires, and is NOT itself sufficient for**: the security/production hardening in this phase (rate limiting, security headers, request-size limiting) is real and tested, but public launch STILL requires the three mandatory legal reviews (decisions.md §5/§6/§9 — none engineering-completable), a load test, a 48h staging soak, and an actual WhatsApp-credentialed live test of the OTP flow. See `docs/risks-and-open-questions.md`'s Phase 7 entry for the complete, honest list.

**Phase 8 additionally requires**: proactive WhatsApp sending for "Check This Tomorrow" (`app/agent/notifications.py`'s `whatsapp` channel) stays hard-blocked — every such notification is written as `blocked_by_policy`, never actually sent — until all three of decisions.md §4/§14 are independently confirmed: Meta requirements, an approved message template, and a budgeted messaging cost model. This is a genuinely separate gate from the §5/§6/§9 legal reviews above; meeting those does not unblock this one. See `docs/risks-and-open-questions.md`'s Phase 8 entry for the complete list of what else is disclosed-but-not-built (fuzzy Explore clustering, Indic-script PDF rendering).

**Phase 9 additionally requires**: a real Postgres/Redis instance and a real deployment (docker-compose or equivalent) — every automated test in this codebase runs against in-memory SQLite and `fakeredis`; neither the full migration cycle nor the rate-limiting/JWT-revocation/OTP-cooldown Redis behavior has ever been verified against the real engines they're designed for. See `docs/production-deployment.md` for the full configuration guide and `docs/risks-and-open-questions.md`'s Phase 9 entry for the complete IMPLEMENTED-vs-LIVE-VALIDATED status of every external dependency. The admin/appeals/moderation system itself does not require a legal review to operate (it is internal trust & safety tooling, not a new public-facing risk surface) — create the first admin account with `python -m scripts.create_admin` after running migrations.
